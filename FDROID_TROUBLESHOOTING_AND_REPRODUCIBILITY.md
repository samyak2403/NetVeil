# F-Droid CI Troubleshooting & Reproducible Builds Architecture Guide

This document provides a complete technical analysis comparing **Repo Store** (`com.samyak.repostore`) and **NetVeil** (`com.samyak.netveil`), explaining the exact root causes behind F-Droid's `Binaries:` and `AllowedAPKSigningKeys:` requirements, and detailing the roadmap to achieving full Reproducible Build parity.

---

## 1. The Core Comparison: Why RepoStore Worked vs Why NetVeil Failed

In your official F-Droid app **Repo Store** (`com.samyak.repostore.yml`):
```yaml
Binaries: https://github.com/samyak2403/RepoStore/releases/download/v%v/app-release.apk
AllowedAPKSigningKeys: dbddc76bf7056f3cfde555c3859c3bbfc31a6f38da89764be9a7633c7e64ce25
```
This configuration **passed** with 0 errors on F-Droid.

### Why RepoStore Succeeded with `Binaries:`
1. **Pure Kotlin / Java Codebase**: RepoStore contains **no C/C++ native code**, no `CMakeLists.txt`, and no Android NDK dependencies.
2. **Deterministic Bytecode**: Standard Java bytecode and Android DEX output generated by D8/R8 are platform-independent. Building on Windows vs building in F-Droid's Debian Linux container produces matching bytecode.
3. **No Native Binaries**: There are no `.so` shared libraries to produce host-OS compiler discrepancies.

---

### Why NetVeil Failed when `Binaries:` was Added
In NetVeil, adding `Binaries:` caused `fdroid build` to fail with:
```
verification of APK with copied signature failed
Comparing reference APK to APK with copied signature...
Unexpected diff output:
diff -r .../META-INF/version-control-info.textproto .../META-INF/version-control-info.textproto
4c4
<   revision: "3893827a7cefe6b937e45dfd2eba7d9e5f9f883d"
---
>   revision: "a9c96d6c3a1409c17d3685c986f04edcd8367f54"
Binary files .../assets/dexopt/baseline.prof differ
Binary files .../classes2.dex differ
Binary files .../lib/arm64-v8a/libnetveil.so differ
Binary files .../lib/armeabi-v7a/libnetveil.so differ
Binary files .../lib/x86/libnetveil.so differ
Binary files .../lib/x86_64/libnetveil.so differ
ERROR: Job failed: exit code 1
```

#### The 3 Underlying Reasons:
1. **C/C++ Native NDK Differences (`libnetveil.so`)**:
   - NetVeil compiles C code using CMake and Android NDK r28c.
   - When compiled on a **Windows** host machine, the Clang compiler embeds Windows-style path separators and Windows DWARF debug symbols into `libnetveil.so`.
   - When F-Droid compiles on **Debian Linux**, Clang uses Linux path separators and Linux debug structures. They are **not byte-for-byte identical**.
2. **Embedded Git Revision Mismatch (`version-control-info.textproto`)**:
   - The release APK on GitHub was built locally when the Git repository was still on commit `3893827a7cefe6b937e45dfd2eba7d9e5f9f883d`.
   - The F-Droid build recipe checks out Git tag `v1.0.1`, which points to commit `a9c96d6c3a1409c17d3685c986f04edcd8367f54`.
   - Android Gradle Plugin automatically embedded the two different commit hashes into each APK.
3. **Prebuilt Tunnel Libraries (`libhev-socks5-tunnel.so`)**:
   - NetVeil bundles prebuilt binaries in `app/src/main/jniLibs/`.
   - In F-Droid, these must be handled via `scanignore:`.

## 2. What F-Droid Official Documentation Says

According to the official [F-Droid Reproducible Builds Documentation](https://f-droid.org/docs/Reproducible_Builds/):
1. **`Binaries:` activates `apksigcopier`**:
   - Specifying `Binaries:` instructs F-Droid to download the developer's pre-compiled APK, compile the app from source on F-Droid's server, strip signatures, and verify that both APKs are **100% identical byte-for-byte**.
   - If a single byte differs (e.g., debug path, timestamp, commit hash), `apksigcopier` rejects the APK and aborts the CI build with exit code 1.
2. **Reproducible Builds are Optional for Inclusion**:
   - Over 70% of applications in F-Droid do **not** use `Binaries:`.
   - For non-reproducible apps, F-Droid compiles from source and signs the APK with the official **F-Droid Repository Signing Key**.
   - When submitting a non-reproducible app, reviewers check the MR checklist:
     ```markdown
     - [ ] Enable Reproducible Builds (RB)
       - [x] If no RB, provide reason: [Documented technical reason]
     ```
   - Reviewer `duckniii` asked *"Why no RB? provide reason"* solely to ensure this checklist requirement was fulfilled.

## 3. How to Enable `Binaries:` & Reproducible Builds for Future NetVeil Releases

To achieve 100% reproducible builds for NetVeil so that `Binaries:` and `AllowedAPKSigningKeys:` pass without diffs in future versions (e.g. `v1.0.2`+):

### Step 1: Disable Dynamic Git Version Metadata
In `gradle.properties`, disable AGP automatic VCS stamping:
```properties
android.enableVersionControlInfo=false
```

### Step 2: Strip Host Paths from C/C++ Compiler
In `app/src/main/cpp/CMakeLists.txt`, pass the file-prefix-map flag to Clang:
```cmake
target_compile_options(netveil PRIVATE -ffile-prefix-map=${CMAKE_SOURCE_DIR}=.)
```

### Step 3: Build Release APKs in Linux CI (GitHub Actions)
Never build official release APKs on a local Windows machine. Create `.github/workflows/release.yml`:
```yaml
name: Build Release APK
on:
  push:
    tags:
      - 'v*'
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK 21
        uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
      - name: Set up Android NDK r28c
        uses: nttld/setup-ndk@v1
        with:
          ndk-version: r28c
      - name: Build Release APK
        run: ./gradlew assembleRelease
```
Because both GitHub Actions and F-Droid will compile on Ubuntu/Debian Linux with the identical NDK r28c toolchain and commit, the resulting APKs will match bit-for-bit.
